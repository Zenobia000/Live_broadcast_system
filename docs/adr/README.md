# 架構決策記錄 (Architecture Decision Records)

本目錄包含智能簽到系統的所有重要架構決策記錄。

## 什麼是 ADR？

ADR (Architecture Decision Record) 是記錄軟體架構決策的輕量級文檔格式。每個 ADR 描述一個具體的架構決策，包括：
- 決策的背景和問題
- 考慮過的選項
- 最終決策和理由
- 決策的後果和影響

## ADR 狀態說明

- ✅ **已接受 (Accepted)**: 決策已被批准並開始執行
- 🔄 **提議中 (Proposed)**: 決策正在討論中
- 🔀 **已取代 (Superseded)**: 決策已被新的 ADR 取代
- ❌ **已棄用 (Deprecated)**: 決策已不再使用
- ⏸️ **暫停 (On Hold)**: 決策暫時擱置

## 何時建立 ADR？

根據 VibeCoding 工作流程和 Linus 實用主義原則，以下情況應建立 ADR：

**必須建立 ADR:**
- ✅ 選擇技術棧或框架
- ✅ 選擇資料庫或儲存方案
- ✅ 選擇認證/授權機制
- ✅ 選擇部署架構或雲服務提供商
- ✅ 重大的 API 設計決策

**建議建立 ADR:**
- 📋 選擇第三方服務整合方案
- 📋 重要的資料模型設計
- 📋 效能優化策略
- 📋 安全性相關決策

**不需要 ADR:**
- ❌ 常規的程式碼重構
- ❌ UI/UX 細節調整
- ❌ 小型的函式庫選擇

## ADR 編號規則

- **ADR-XXX**: 一般架構決策（從 001 開始）
- **ADR-WBS-XXX**: 與 WBS 變更相關的決策

## 💡 Linus 的建議

> "ADR 不是為了寫文檔而寫文檔。它是為了記住「為什麼」。
>
> 六個月後，當你看著某段程式碼想『當初為什麼要這樣做？』時，ADR 會告訴你答案。
>
> 但別過度記錄。只記錄那些『如果出錯會很痛』或『將來可能需要改變』的決策。
>
> 記住：程式碼是會說話的文檔，好的 ADR 解釋的是程式碼不能告訴你的『為什麼』。"
