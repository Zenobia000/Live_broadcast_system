## 第 2 部分：商業目標 (Business Objectives) - 「為何做？」

*在投入資源前，我們必須清晰地定義問題、目標使用者和商業價值，避免開發出無人需要的產品。*

| 區塊 | 內容 |
| :--- | :--- |
| **1. 背景與痛點** | *現行市場簽到系統普遍存在體驗分散、審核延遲、行為驗證弱、跨平台整合困難、報表不即時等問題。使用者需要在多個系統間切換（如行事曆、請假單、簽到App），管理者也因流程繁瑣而耗費大量時間進行人工審核與統計，導致整體效率低落。* |
| **2. 策略契合度** | *本專案旨在打造一個以事件驅動為核心的自動化簽到與智能審核平台，無縫整合行事曆，提升團隊管理效率與成員的數位化體驗，符合公司推動內部流程自動化的戰略目標。* |
| **3. 成功指標 (Success Metrics)** | *我們如何衡量成功？定義 1-3 個可量化的關鍵績效指標 (KPI)。* <br> - **主要指標**: 自動簽到成功率達到 99% 以上。<br> - **次要指標**: 人工審核（補簽/請假）需求降低 80%。 |

## 第 4 部分：範圍與限制 (Scope & Constraints)

*明確定義邊界是專案成功的關鍵。這為 LLM 生成程式碼提供了最重要的「護欄」。*

| 區塊 | 內容 |
| :--- | :--- |
| **功能性需求 (In Scope)** | *高層次功能列表，將依敏捷開發步驟迭代交付。*<br> - **MVP (Sprint 1)**: 使用者認證 (Google OAuth)、登入後自動簽到。<br> - **Sprint 2**: 請假與補簽申請流程、管理員審核介面。<br> - **Sprint 3**: Google Calendar 行事曆整合、Email/Slack 通知。<br> - **Sprint 4**: UI/UX 優化 (Apple 風格)、Dashboard 出缺勤報表。 |
| **非功能性需求 (NFRs)** | *系統必須滿足的品質屬性。*<br> - **性能**: 簽到與狀態更新需在 1 秒內完成，達到即時同步。<br> - **安全性**: 所有身份驗證基於 OAuth 2.0，不儲存使用者原始密碼。<br> - **可用性**: 介面設計遵循 Apple Human Interface Guidelines，確保簡潔易用。 |
| **不做什麼 (Out of Scope)** | *明確列出本次不做的事項，以避免範圍蔓延。*<br> - 不支援人臉辨識或 GPS 定位簽到。<br> - 不支援與企業內部 ERP/薪資系統對接。<br> - 不支援除了 Google Calendar 以外的其他日曆服務 (如 Outlook) 的雙向同步。 |
| **假設與依賴** | *我們基於哪些假設？專案依賴哪些內部或外部服務？*<br> - **假設**: 目標使用者群體均擁有 Google 帳號。<br> - **依賴**: 專案強烈依賴 Google Calendar API 的穩定性。 |
